# リリースノート・更新履歴を書く

開発者の視点（コミットの内容）ではなく、利用者にとって何が変わるかで書く。分類して読みやすくする。

## 先に確認すること
- バージョン番号と日付
- 変更点の一覧（コミット、メモ）
- 対象の読み手（一般利用者、開発者）
- 重大な変更（互換性）

## 手順
1. 変更を、追加・変更・修正・削除・セキュリティに分類する。
2. 各項目を、利用者の言葉で一文にする。
3. 互換性を壊す変更は、冒頭で目立たせ、移行方法を書く。
4. 関連するIssueや課題の番号を添える。
5. 日付とバージョンを明記する。
6. 内部の変更（リファクタリング）は、省略するか別枠にする。

## 出力形式
```
## {バージョン} ({日付})
### 追加
### 変更
### 修正
### 削除
### 注意（互換性）
```

## 例
入力：「v1.3.0。履歴の検索機能を追加。保存時にフリーズする不具合を修正。古い設定ファイルの形式は非対応に」
出力のポイント：
- 追加：履歴の検索機能。修正：保存時にフリーズする不具合。
- 注意：古い設定ファイルの形式は非対応（移行方法を要記入）。

## 注意
- 入力に無い変更を作らない。
- 日付と番号の正確さを、確認するよう添える。
